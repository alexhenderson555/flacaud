# Архитектура проекта FlacAud

Данный документ описывает высокоуровневую архитектуру платформы **FlacAud**, включая взаимодействие компонентов, выбор технологий и паттерны проектирования. Архитектура разработана с упором на масштабируемость, высокую производительность (как на клиенте, так и на сервере) и способность обрабатывать ресурсоемкие ML-задачи.

## 🏗 Общая схема

Проект состоит из трех основных слоев:
1. **Frontend (Client App)** — Single Page Application (SPA), обеспечивающее пользовательский интерфейс, 3D-графику и воспроизведение аудио.
2. **Backend (API Layer)** — RESTful API, обрабатывающее бизнес-логику, авторизацию и взаимодействие с базой данных.
3. **Background Workers & ML** — Изолированные воркеры для выполнения тяжелых задач (скачивание аудио, ML-обработка).

---

## 💻 Frontend Архитектура

Клиентское приложение построено на базе **React 19** и собирается с помощью **Vite**.

### 1. Управление состоянием
Для глобального состояния используется **Zustand**. Выбор обусловлен его минимальным API, отсутствием boilerplate-кода и отличной производительностью при частых обновлениях (например, позиция воспроизведения плеера). Состояние разделено на логические слайсы (PlayerStore, LibraryStore, UIStore).

### 2. Рендеринг и Производительность
- **Виртуализация**: Для рендеринга больших списков (тысячи треков в библиотеке) используется **@tanstack/react-virtual**. Это позволяет держать в DOM только видимые элементы, гарантируя стабильные 60 FPS при скроллинге.
- **Анимации**: **framer-motion** управляет всеми сложными UI-переходами (открытие плеера, переходы между страницами), предоставляя физически обоснованные анимации.

### 3. Воспроизведение и Графика
- **Gapless Playback**: Реализован через Web Audio API путем предзагрузки и буферизации следующего трека до окончания текущего, исключая задержки при переключении.
- **3D WebGL Party Mode**: Модуль аудио-визуализации написан с использованием **react-three-fiber**. Аудио-контекст анализируется в реальном времени, а данные о частотах передаются в шейдеры для управления геометрией и освещением 3D-сцены.

## ⚙️ Backend Архитектура

Серверная часть спроектирована вокруг асинхронности и строгой типизации с использованием **FastAPI**.

### 1. Веб-слой и API
**FastAPI** обрабатывает входящие HTTP-запросы. Благодаря Pydantic валидация данных происходит на лету, а спецификация OpenAPI генерируется автоматически. Приложение использует Dependency Injection для предоставления сессий базы данных и сервисов авторизации в эндпоинты.

### 2. Слой данных (Database)
- В качестве ORM применяется **SQLModel** (надстройка над SQLAlchemy и Pydantic), что позволяет использовать одни и те же модели данных как для базы данных, так и для валидации API.
- База данных (PostgreSQL) хранит метаданные треков, плейлисты, информацию о пользователях и статусы фоновых задач.

### 3. Фоновые задачи и Очереди (ARQ + Redis)
Поскольку загрузка Lossless-аудио и работа моделей машинного обучения могут занимать минуты, эти задачи выполняются асинхронно.
- **ARQ** (на базе **Redis**) выбран как легковесная и очень быстрая альтернатива Celery.
- **Воркеры**: При запросе на скачивание или обработку трека FastAPI-сервер помещает задачу в очередь Redis. ARQ-воркер забирает задачу, выполняет её и обновляет статус в БД. Frontend получает статус задачи через поллинг или WebSocket.

## 🧠 Machine Learning и Аудио-процессинг

Для предоставления уникального пользовательского опыта (Stem Splitting) в бэкенд интегрированы ML-модели:
- **Demucs**: State-of-the-art модель глубокого обучения от Meta Research для разделения музыкальных треков на изолированные дорожки (стемы: вокал, ударные, бас, другие). Воркер загружает скачанный FLAC файл в модель, выполняет инференс (желательно с использованием GPU) и сохраняет полученные аудиофайлы на диск или в S3-совместимое хранилище.
- **aubio**: Библиотека для анализа аудиосигналов. Используется для извлечения метаданных, определения темпа (BPM) и тональности трека на сервере.

## 🐳 Инфраструктура и Развертывание

Весь стек контейнеризирован с помощью **Docker**, что обеспечивает консистентность между development и production средами.

### Docker Compose Services:
1. **api**: FastAPI бэкенд.
2. **worker**: ARQ-воркер, загружающий ML-модели и выполняющий тяжелую обработку.
3. **db**: PostgreSQL для хранения данных.
4. **redis**: In-memory хранилище для брокера очередей ARQ.
5. **client**: (Опционально для production) Nginx-контейнер, отдающий статические файлы собранного React-приложения.

Такая микросервисная архитектура позволяет горизонтально масштабировать отдельные узлы. Например, при высокой нагрузке на обработку аудио можно легко запустить дополнительные экземпляры `worker` контейнеров на серверах с мощными GPU.

## 🎧 Плеер и стриминг (Frontend + API)

### Слой воспроизведения

- **`PlayerLogic.jsx`** — подключает хуки без UI: auth, quality, transport, persistence → Zustand `usePlayerStore`.
- **`GlobalAudio.jsx`** — два физических `<audio>` (main + preload) для gapless; watchdog `shouldStartPlayback` устраняет «второй клик».
- **`usePlayerTransport`** → `usePlayerQueue`, `usePlayerProgressLoop`, `usePlayerRadio`.

### Качество звука

1. **Probe:** `GET /api/quality/{provider}/{id}/available` — анализ codecs в DASH manifest.
2. **Stream:** `GET /api/stream/...?quality=&mt=` — tier ограничивается планом (`cap_stream_quality`).
3. **`usePlaybackQuality`** — `changeQuality` всегда форсирует reload (`streamRetryNonce`); в **auto**-режиме смена tier откладывается только при активном play.
4. UI в стабильном состоянии показывает **фактически доставленный** tier (`resolvePlayerUiQuality`).

### Режимы отдачи (backend)

| `X-Stream-Mode` | Описание |
|-----------------|----------|
| `redirect` | Range на CDN Tidal |
| `dash_stream` | DASH → remux на диск → byte-range (полный файл до первого ответа) |
| `file` | Локальный кэш / downloaded registry |

Подробнее: [docs/FEATURES.md](./docs/FEATURES.md) §2.

## 🖼 Медиа и портреты артистов

### Image proxy

Фронтенд не ходит на внешние CDN напрямую (CORS/VPN). Все обложки и портреты — через **`GET /api/image-proxy?url=`**.

**SSRF-защита** (`routers/media.py`):

- Только `http`/`https`
- DNS → отклонение private / loopback / link-local
- Allowlist суффиксов: Tidal CDN, Wikimedia/Wikipedia, Deezer (`dzcdn.net`), Apple (`mzstatic.com`)

### Цепочка портретов (`artist_image.py`)

Без платных API и без ключей:

1. Wikipedia / Wikimedia (ru/en по имени)
2. Deezer Search API
3. iTunes Search API (upscale artwork)
4. Fallback — picture из Tidal catalog

In-memory кэш 7 дней (`artist_image_cache.py`, `TIDALDLRU_ARTIST_IMAGE_CACHE_TTL`). Ответ каталога: `picture_url`, `picture_source`.

## 📻 Рекомендации и Genre Radio

Модуль **`server/recommendations.py`**:

- Персональные треки — сигналы библиотеки + Tidal stubs, TTL-кэш.
- **Genreverse** — бесконечное radio по genre/mood.

**Обогащение обложек:** radio/similar stubs часто шарят один UUID cover → `_finalize_track_covers` делает batch `get_track` для уникальных art URL. Фронт: `enrichTracksFromApi` в `Genreverse.jsx`.

## 📦 Деплой и edge

- **Caddy** отдаёт `frontend/dist` (`/assets/*` immutable), проксирует `/api/*` на uvicorn; gzip выключен для stream (Range/206).
- Деплой: `scripts/deploy_tidal.py` — режимы **tar** (сборка на VPS) или **registry** (Docker Hub). См. [docs/DEPLOY.md](./docs/DEPLOY.md).
- Tidal egress из RU — через отдельный VPS (Marzban/Xray); не в коде приложения.
